# Регистратор аудио-инцидентов (гром/сирены/хлопки)

ESP32-S3 N16R8 + 2x INMP441 (I2S-микрофоны, стерео, смонтированы ВЕРТИКАЛЬНО)
+ ILI9341 240x320 (SPI TFT) + microSD. Слушает постоянно, определяет сирены
(длительность + паттерн: непрерывная / несколько отрезков / короткая-длинная)
и хлопки (гроза / выстрел / взрыв / удар по металлу — эвристическая
классификация), плюс громкость (дБFS) и грубую оценку угла места
(снизу/сверху — см. раздел "Направление/высота источника" ниже), выводит на
экран и пишет CSV-лог + WAV каждого события на SD.

Собрано и реально скомпилировано (arduino-esp32 core 2.0.9, `--warnings all`
— 0 ошибок, 0 предупреждений) под `esp32:esp32:esp32s3` с `PSRAM=opi,
FlashSize=16M`. Также прогонялось на реальном ESP32-S3 (arduino-esp32 core
3.3.10) — см. "Текущий статус" ниже: часть подсистем подтверждена рабочей,
по экрану есть открытая проблема. Пороги детекции (сирена/хлопок/громкость)
пока не откалиброваны под конкретное место установки — это отдельный шаг,
см. раздел "Калибровка" ниже.

## Текущий статус

Подтверждено рабочим на реальном железе (ESP32-S3, arduino-esp32 core
3.3.10): старт/вотчдог, Wi-Fi + NTP, SD (определение отсутствия карты без
падения), захват звука по I2S (`AudioCapture::begin()`). PSRAM нужно включить
вручную (Tools -> PSRAM: OPI PSRAM) — без этого `EventDetector::begin()`
корректно откажется стартовать с понятным сообщением, это не баг.

**Открытая проблема:** `DisplayUI::begin()` (конкретно `tft.init()` из
TFT_eSPI 2.5.44) стабильно роняет устройство в `Guru Meditation Error
(StoreProhibited)` на core 3.3.10 — локализовано контрольными точками в
Serial и безопасным режимом (см. "Устойчивость к сбоям" ниже), причина пока
не подтверждена на 100% (подозрение — несовместимость TFT_eSPI 2.5.44 с SPI-
драйвером core 3.x/IDF5, возможно связано с DMA). Устройство не зависает
намертво — после 3 падений подряд само переходит в безопасный режим и
работает без экрана. Если доберётесь до причины (или обновление TFT_eSPI
её решит) — это первое, что стоит проверить перед релизом с экраном.

## Пины (сверить с шёлкографией вашей платы!)

| Сигнал | GPIO |
|---|---|
| I2S BCLK (оба мика) | 4 |
| I2S WS (оба мика) | 5 |
| I2S DIN (оба мика, вход) | 6 |
| TFT SCLK | 12 |
| TFT MOSI | 11 |
| TFT MISO | 13 |
| TFT CS | 10 |
| TFT DC | 9 |
| TFT RST | 8 |
| TFT BL (подсветка) | 14 |
| SD CS | 21 |

TFT и SD сидят на одной физической SPI-шине (SCLK/MOSI/MISO общие), у каждого
свой CS — это нормально и не мешает друг другу. Оба INMP441 сидят на ОДНОЙ и
той же I2S-шине (BCLK/WS/DIN общие, новых GPIO не требуется) — единственное
отличие между ними: вывод L/R (SEL) первого (нижнего) микрофона впаян на GND
("L"-канал), второго (верхнего) — на VDD ("R"-канал). Микрофоны монтируются
**вертикально**: нижний — у самого устройства, верхний — на мачте выше на
`MIC_SPACING_M` (по умолчанию 1.0м, см. раздел "Направление/высота источника"
ниже); если после монтажа "снизу/сверху" на экране окажутся перепутаны — не
перепаивайте, поставьте `MIC_SWAP_CHANNELS 1` в `config.h`. Разная длина
кабеля до нижнего и верхнего микрофона не мешает измерению (см. комментарий в
`config.h`) — важно только использовать экранированный кабель и не давать
ему провисать/хлопать на ветру. На платах с Octal PSRAM (N16R8/R8) GPIO 33-37
заняты внутренней шиной к PSRAM/flash — занятые пины ниже их не используют,
но перепроверьте по факту, если распиновка вашей конкретной платы отличается
от типового ESP32-S3-DevKitC-1 (см. историю с ESP32-2432S028 в заметках
проекта — готовые платы разных производителей иногда сильно расходятся).

## Настройка окружения (Arduino IDE)

1. Board Manager URL: `https://raw.githubusercontent.com/espressif/arduino-esp32/gh-pages/package_esp32_index.json`,
   поставить платформу **esp32 by Espressif Systems**.
2. Плата: **ESP32S3 Dev Module**.
3. Tools -> **PSRAM: "OPI PSRAM"** — обязательно, без этого буферы захвата
   (в PSRAM) не выделятся и прошивка откажется стартовать с ошибкой в Serial.
4. Tools -> Flash Size: **16MB**, Partition Scheme — любая под 16MB с
   достаточным местом под APP (использовано ~800КБ из ~3МБ при варианте
   `app3M_fat9M_16MB`, есть большой запас).
5. Библиотека **TFT_eSPI** (Bodmer) — после установки нужно вручную открыть
   `<sketchbook>/libraries/TFT_eSPI/User_Setup.h` и прописать туда пины из
   таблицы выше (см. `TFT_MISO/MOSI/SCLK/CS/DC/RST` + `#define ILI9341_DRIVER`,
   `TFT_WIDTH 240`, `TFT_HEIGHT 320`) — TFT_eSPI конфигурируется на этапе
   компиляции, а не в скетче. **Если поменяете пины в `config.h` — поменяйте
   и здесь**, иначе экран останется на старых пинах. **Туда же обязательно
   добавить `#define LOAD_GFXFF`** — без него в библиотеке не объявляются
   типы `GFXglyph`/`GFXfont`, которые нужны кириллическому шрифту
   (`cyr_font.h`), и сборка упадёт с чередой малопонятных ошибок вида
   `'GFXglyph' does not name a type` (сам `cyr_font.h` теперь проверяет это
   и выдаёт одну ясную ошибку вместо каскада — но лучше сразу не забыть).
6. `SD`, `SPI`, `WiFi` — идут в комплекте с ядром esp32, отдельно ставить не
   нужно.
7. В `config.h` вписать `WIFI_SSID`/`WIFI_PASSWORD`.

**Версия ядра esp32 (arduino-esp32):** прошивка собрана и проверена под core
2.0.9 (ESP-IDF 4.4). Свежие установки Arduino IDE обычно ставят более новый
core на базе IDF5 (например 3.x) — код совместим с обеими ветками (см.
`watchdog_diag.cpp`, там есть проверка версии IDF), но целиком под IDF5
здесь не пересобирался (нет такой возможности в этом окружении), поэтому
если вылезет что-то специфичное именно для IDF5 — присылайте лог ошибки,
поправим.

## Как это работает вкратце

- Постоянный энергетический детектор с адаптивным порогом фона (медленно
  подстраивается под тишину, замирает на время события).
- Пре-ролл буфер 0.5с в PSRAM — чтобы не терять начало резкого фронта хлопка.
- Пока событие громкое, параллельно проверяется "тональность" в полосе
  500-1500 Гц (банк Гёрцеля). Если тон держится >= 1.2с — событие признаётся
  сиреной; дальше для неё не хранится весь сырой звук (сирена может длиться
  минуты), а только сегменты вкл/выкл для описания паттерна плюс короткий
  представительный WAV-фрагмент начала.
- Если тон не подтвердился — по окончании события (300мс тишины) это
  "хлопок": считаются признаки (фронт, спад, энергия по трём полосам,
  ZCR, второй импульс) и взвешенным правилом относится к одной из категорий
  (гроза/выстрел/взрыв/металл) — см. `bang_classifier.cpp`.
- Каждое событие: строка в `/events.csv` + WAV в `/events/`.

## Громкость (дБFS)

Кроме длительности, для каждого события считается громкость — пиковая
(`peakDbfs`, максимум за всё событие) и средняя (`avgDbfs`, по RMS за всё
событие). Оба значения — **дБFS (decibels relative to Full Scale)**, то есть
относительно максимума шкалы 16-битного АЦП микрофона (0 дБFS = цифровой
клиппинг, дальше вниз — тише; типично звук событий будет в районе от −40 до
−5 дБFS). **Это не калиброванный dB SPL** (абсолютный уровень звукового
давления, как на бытовом шумомере) — у INMP441 нет откалиброванной по месту
чувствительности, поэтому абсолютные "физические" децибелы честно посчитать
нельзя без отдельной калибровки эталонным источником звука. дБFS выбран
вместо совсем грубого "порядок величины", потому что это стандартная в
аудиотехнике шкала, дёшево считается из уже захваченных данных (пик и
среднеквадратичное по кадрам) и достаточно точна для сравнения событий между
собой ("это было громче того") — что и является практической целью.

Где это видно:

- На экране в строке лога события — пиковое значение, округлённое до
  целого дБ (`%.0fдБ`), для быстрого взгляда на "насколько было громко".
  В статусной строке во время самого события — тоже пиковое, обновляется
  на лету.
- В `/events.csv` — оба значения отдельными колонками (`peak_dbfs`,
  `avg_dbfs`), для более полного анализа задним числом.
- В Serial-логе — оба значения в отладочной строке при завершении события.

Реализация — `loudness.h/.cpp` (`Loudness::toDbfs()`) + накопление
суммы квадратов RMS по кадрам события в `event_detector.cpp`
(`s_rmsSquaredAccum`/`s_activeFrameCount`, обнуляются в начале события,
итог считается в `finishEvent()`).

## Направление/высота источника (снизу/сверху)

Второй микрофон (см. таблицу пинов выше) смонтирован **вертикально** —
выше первого на мачте — и даёт грубую оценку "источник звука ниже линии
микрофонов или выше неё" по разнице времени прихода одного и того же звука
в нижний и верхний канал (TDOA — time difference of arrival), считается
кросс-корреляцией сырых каналов при старте каждого события.

Изначально (08.09.2026) второй микрофон ставился горизонтально ради
лево/право; по итогам разбора (25.09.2026, см.
`audio-incident-recorder-design.md` в проекте narodmon) решили, что для
этой задачи полезнее вертикальный монтаж — различать "гроза высоко в небе" /
"бахнуло рядом на земле" / "бахнуло вдали и высоко (что-то в воздухе)".
Лево/право при таком монтаже не определяется — ось одна, и её отдали под
угол места.

**Это не компас и не дальномер.** Пара микрофонов даёт направление только
вдоль своей оси (линии между микрофонами) — здесь ось вертикальная, поэтому
измеряется угол места, а не азимут: метод в принципе не может сказать, с
какой стороны горизонта пришёл звук, только "насколько он выше или ниже
уровня микрофонов". Расстояние до источника из одного угла места не
получить без дополнительных допущений — угол зависит от ОТНОШЕНИЯ высоты
источника к дальности, а не от дальности отдельно (например, "50м высоты на
1км" и "5м высоты на 100м" дают один и тот же угол) — подробный разбор с
расчётами см. в заметках проекта.

Точность зависит от `MIC_SPACING_M` (config.h) — реального расстояния между
нижним и верхним микрофоном: чем больше база, тем точнее оценка, но и тем
длиннее/тяжелее консоль на мачте. По умолчанию стоит 1.00м — разумный
компромисс по расчётам в заметках проекта (уверенно различает грозу, наземные
события и события в воздухе на высоте от ~100м на дистанции до 1км) —
**обязательно поправьте на реальное измеренное расстояние после монтажа**,
иначе оценка будет систематически смещена. Расстояния существенно больше
1.5-2м обычно не имеют смысла — выигрыш в точности начинает уступать
практическим минусам (длиннее мачта, хуже корреляция между далеко
разнесёнными микрофонами на открытом воздухе).

Где это видно:

- На экране — короткая буква в конце строки лога и в статусной строке:
  **Н** (снизу), **В** (сверху), **Ц** (по центру/неоднозначно), **?**
  (не определено — например, PSRAM для буфера направления не выделилась).
- В `/events.csv` — три колонки: `direction` (текстом), `direction_delay_ms`
  (сырая измеренная задержка, для калибровки), `direction_confidence` (0..1).
- В Serial-логе — то же самое при завершении события.

Если "снизу/сверху" на экране оказались перепутаны местами (например,
из-за того, как реально распаялась плата, или порядка слотов, который
отдаёт I2S-периферия конкретной платы — без реального железа под рукой
гарантировать его нельзя) — не нужно перепаивать провода, достаточно
поставить `MIC_SWAP_CHANNELS 1` в `config.h` и перепрошить.

Реализация — `direction.h/.cpp`: кольцевой буфер L/R в PSRAM (аналог
mono-преролла), снимок последних `DIRECTION_WINDOW_SEC` секунд в момент
старта события (`event_detector::startEvent()`, пока фронт атаки ещё свежий
в буфере), нормированная кросс-корреляция по сдвигам, ограниченным физически
возможной задержкой при заданном `MIC_SPACING_M`.

## Калибровка (обязательный шаг после установки)

Пороги в `config.h` и веса в `bang_classifier.cpp` — стартовое инженерное
приближение, не результат обучения на реальных записях (см.
`audio-incident-recorder-design.md` в проекте narodmon — там подробно
разобрано, почему 100% точность на одном микрофоне в принципе недостижима).
После установки:

1. Дайте устройству поработать несколько дней в тишине — проверьте по
   `/diag.log` и Serial, что оно не срабатывает на бытовые звуки (лай,
   проезжающие машины). При частых ложных срабатываниях поднимите
   `THRESH_START_RATIO` в `config.h`.
2. Прослушайте накопленные WAV из `/events/` — сверьте с тем, что реально
   классифицировал `bang_classifier` (см. `/events.csv`). Если система
   систематически путает, например, взрыв с грозой — донастройте пороги в
   `bang_classifier.cpp` (они помечены `TUNE ME`) под конкретные записанные
   примеры.
3. Если рядом бывают реальные сирены — сверьте `patternText` из лога с тем,
   что было на самом деле, и при необходимости подправьте `TONE_RATIO_THRESHOLD`
   / `TONE_CONFIRM_SEC` / пороги сегментации (`SEG_END_FRAMES` в
   `event_detector.cpp`).
4. Угол места: подставьте в `MIC_SPACING_M` (config.h) реальное измеренное
   расстояние между нижним и верхним микрофоном. Затем сверьте несколько
   заведомо разных по высоте звуков (например, хлопок у земли рядом с
   устройством и хлопок/звук, заведомо поднятый выше верхнего микрофона —
   с шеста, с крыши и т.п.) с тем, что показал экран/лог — если "снизу" и
   "сверху" перепутаны, поставьте `MIC_SWAP_CHANNELS 1` (см. раздел
   "Направление/высота источника" выше), перепайка не нужна. Также имеет
   смысл сверить показания на реальной грозе и на заведомо близких наземных
   бахах — это и есть основной сценарий использования (см. заметки проекта).

## Русский текст на экране

Встроенные шрифты TFT_eSPI — только ASCII (латиница/цифры), кириллицы в них
нет в принципе. Поэтому весь текст на экране рисуется кастомным шрифтом
`cyr_font.h`: сгенерирован скриптом `tools/gen_cyr_font.py` из DejaVu Sans
Bold (Pillow/FreeType) в формате GFXfont (тот же формат, что "free fonts" у
Adafruit_GFX/TFT_eSPI — подключается через `LOAD_GFXFF`, уже включено в
`User_Setup.h`).

Т.к. GFXfont адресует глифы однобайтовым кодом (0-255), а кириллица в
UTF-8 — многобайтовая, кириллические буквы зашиты в диапазон 0xC0-0xFF (и
Ё/ё в 0xA8/0xB8) — **это ровно раскладка кодовой страницы Windows-1251**, не
самопальная. Перед выводом любая строка проходит через `utf8ToCp1251()`
(`cyr_convert.h`) — это уже сделано внутри `display_ui.cpp` для всех
экранных надписей, руками вызывать не нужно, если просто меняете текст в
существующих местах.

Если добавите новую надпись на экран с русским текстом — ничего специально
делать не нужно (конвертер универсальный), *если* используются буквы,
уже покрытые шрифтом (весь алфавит А-Я/а-я + Ё/ё + ASCII 0x20-0x7E — то
есть практически любой русский текст без экзотических символов вроде «№»
или «©»). Если понадобится расширить набор символов — правьте
`build_charmap()` в `tools/gen_cyr_font.py` и перезапустите генератор
(`python3 tools/gen_cyr_font.py`, нужны Pillow и шрифт DejaVu Sans на
машине, где генерируете) — он же перезапишет `cyr_font.h` и заново сохранит
self-check PNG (`tools/cyr_font_selfcheck.png`) для визуальной проверки, что
битовая упаковка не сломалась (стоит сверять глазами после любого изменения
шрифта — на реальном экране это не проверить без платы в руках).

## Устойчивость к сбоям при первом включении

При первых реальных прошивках на новое железо (особенно "голая" плата с не
до конца распаянной периферией) устройство может упасть в Guru Meditation
Error сразу после старта и уйти в бесконечный цикл перезагрузок, ничего не
написав в Serial. Чтобы это не было "чёрным ящиком", в прошивку добавлено
несколько уровней защиты.

**Найденная и исправленная реальная причина одного такого падения.**
На тестовом железе (ESP32-S3, ILI9341 по SPI) устройство стабильно падало в
`Guru Meditation Error: Core 1 panic'ed (StoreProhibited)` сразу после
`SPI.begin()` в `setup()`, ещё до `DisplayUI::begin()`. Причина: `.ino`
сам вызывал `SPI.begin(SCLK, MISO, MOSI, PIN_TFT_CS)` (для "общей шины с
SD"), а следом `tft.init()` внутри `DisplayUI::begin()` вызывает `SPI.begin()`
ВТОРОЙ раз, уже с другим SS-пином (-1) — TFT_eSPI на ESP32-S3 без явного
`USE_HSPI_PORT`/`USE_FSPI_PORT` в `User_Setup.h` использует ссылку на тот
же самый глобальный объект `SPI` (см.
`TFT_eSPI/Processors/TFT_eSPI_ESP32_S3.c`, строка `SPIClass& spi = SPI;`).
Повторный `begin()` одного и того же `SPIClass` с другим набором аргументов
ронял устройство. Исправлено: `SPI.begin()` теперь вызывается РОВНО ОДИН
РАЗ — либо внутри `tft.init()` (обычный режим), либо явно в
`DisplayUI::begin()` теми же пинами, если экран отключён безопасным
режимом (см. ниже). В `.ino` свой отдельный вызов `SPI.begin()` убран.
Если в вашей сборке `TFT_eSPI` используется другой порт SPI
(`USE_HSPI_PORT`/`USE_FSPI_PORT` в `User_Setup.h`) — двойного `begin()` на
одном объекте не будет, но лишний вызов всё равно не нужен.

Дополнительно, независимо от этой находки, в прошивку добавлено несколько
уровней защиты на случай ДРУГИХ, ещё не встреченных проблем со стартом:

- **Контрольные точки в Serial.** `setup()` печатает `[main] checkpoint: ...`
  после КАЖДОГО шага инициализации (вотчдог, проверка PSRAM, экран (внутри
  которого поднимается и SPI-шина, см. выше), Wi-Fi, SD, микрофоны,
  детектор). Если устройство падает — в мониторе
  порта видна последняя пройденная контрольная точка, и сразу понятно, на
  каком именно шаге, без разбора backtrace через addr2line.
- **Проверка PSRAM в начале `setup()`.** Если `ESP.getPsramSize() == 0`,
  сразу печатается явное предупреждение проверить Tools -> PSRAM: "OPI
  PSRAM" — не нужно ждать, пока до этого доберётся `EventDetector::begin()`.
- **Диагностика связи с экраном.** `DisplayUI::begin()` после инициализации
  читает ID-регистр экрана через SPI (безопасная read-транзакция, ничего не
  меняет) и печатает в Serial, отвечает ли экран вообще — если ID пришёл
  "залипшим" (0x00/0xFF), это явный признак, что ILI9341 не подключён или
  не разведён MISO.
- **Безопасный режим после серии падений подряд.** Счётчик в RTC-памяти
  (переживает программный резет/панику, `watchdog_diag.h`) считает подряд
  идущие перезагрузки с причиной "паника/сторожевой таймер". После 3 подряд
  устройство на следующей загрузке само отключает инициализацию экрана
  (`DisplayUI::setEnabled(false)`) и продолжает работать без него — слушает
  звук, пишет на SD, статус дублируется в Serial (`[display] статус: ...`)
  вместо отрисовки. Если причиной падений был именно экран — устройство
  "выживет" само, без разборки в полевых условиях. Счётчик сбрасывается,
  если загрузка проработала стабильно 20 секунд (`markBootStable()`), так
  что один случайный сбой через месяцы работы не включит безопасный режим
  навсегда.
- **Вотчдог кормится и в "залипших" ветках.** Если `AudioCapture::begin()`
  или `EventDetector::begin()` не смогли стартовать (нет микрофонов / нет
  PSRAM), устройство раньше зависало в `while(true) delay(1000)` молча — то
  есть кормёжка вотчдога прекращалась, и через `WDT_TIMEOUT_SEC` сверху
  добавлялась ещё одна, уже совсем непонятная перезагрузка. Теперь эти
  ветки кормят вотчдог и раз в 5 секунд повторяют причину остановки в
  Serial — устройство честно "висит и говорит, почему", а не тихо
  перезагружается по кругу поверх уже понятной ошибки.

Если после всего этого падение по-прежнему происходит ДО первой
контрольной точки в Serial (т.е. сразу после банера "=== Регистратор...
==="), возможная точка отказа сужается до `WatchdogDiag::begin()` — тогда
уже нужен разбор backtrace через `addr2line` по адресам из вывода паники и
файлу `.elf` из папки временной сборки Arduino IDE.

## Известные ограничения v1

- WiFi/пароль — константы в `config.h`, без веб-конфигурации (`/settings`
  как в weather_display можно добавить отдельным шагом).
- RTC нет — время только по NTP (осознанное решение, т.к. Wi-Fi на месте
  установки всегда доступен).
- Классификация хлопков — эвристика на акустических признаках, не
  нейросеть. WAV каждого события сохраняется намеренно, чтобы можно было
  вручную переразметить и при желании позже обучить модель (см. заметки
  проекта, раздел про TFLite Micro).
- Направление — только угол места снизу/сверху (одна вертикальная ось, не
  компас и не дальномер — расстояние до источника из угла места не
  получить), не откалибровано под реальное расстояние между микрофонами
  (нужно подставить `MIC_SPACING_M` после монтажа на мачте) и не проверено
  на реальном железе в таком (вертикальном) варианте монтажа. См. раздел
  "Направление/высота источника" выше.
